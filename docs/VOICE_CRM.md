# Voice Agent workspace

CRM staff use **Voice Agent** to inspect the Opek phone agent, edit its configuration,
read calls and recordings, and work qualified leads. E2 customer access is unchanged.
The existing Inbound calls report keeps historical provider records.

## Staff workflow

- Overview shows the assigned phone/deployment, models, published and last observed
  revisions, and call/lead/confirmed-booking totals. Observation is not an uptime SLA.
- Configuration keeps an independent draft. Save, then explicitly publish for new
  calls. Concurrent edits return a conflict instead of overwriting another editor.
  Rollback publishes a copy of an earlier revision without overwriting the draft.
- Calls supports search, status and date filters, private playback/download,
  transcripts, outcomes and links to contact conversations and confirmed bookings.
  Calls without usable callback details remain visible for staff follow-up.
- Leads reuses the existing open/assigned/resolved/closed workflow. Repeated calls
  link to an open lead; they do not reset staff assignment or overwrite contact names.
  Caller ID and supplied callback numbers are unverified. Recording an inquiry
  never sends SMS, grants consent, enrolls a follow-up or reserves a booking.
- Availability stays in Booking setup. Voice booking still requires enabled rules
  and the separate deployment feature flag. Conversational SMS remains inactive.

## Contracts and security

`GET /api/voice` returns staff-only agent/configuration metadata and totals.
`GET /api/voice/{calls,leads,call,media}` supplies paginated lists or an `id` detail.
`POST /api/voice/{initialize,save,publish,rollback}` manages configuration. Save and
publish require `agentId` and `version`; save takes `configuration`, rollback takes
`revision`. Initialize is an operator import of the verified existing deployment.
Configuration fields are `name`, `persona`, `voice`, `brain`, and `voiceName`.
Credentials, routing and model identifiers are not editable through this workspace.

`voice-runtime` uses a separate HMAC secret and restricted SQL login. Its envelope
is `{action,callId,payload}`; business and agent are pinned server-side. Operations
are configuration, start, heartbeat, finish, outcome, upload and uploaded. It cannot
publish, confirm bookings, invoke legacy write tools or read arbitrary customers.
Recording paths are generated by the database; the Edge handler checks uploaded
object size and MIME before finalization. The worker receives only signed upload
URLs, never a database or storage master key. Existing lookup/booking roles retain
their original boundaries. Published configuration and media reads are audited.

Private tables retain agent/configuration/call metadata; audio is in the private
`voice-recordings` Storage bucket. The generic contact/call APIs are not expanded
to expose this content. Media URLs last five minutes. Audio and full CRM transcripts
expire after 90 days; metadata, summaries, leads and booking relationships remain.
`voice-maintenance` retries object deletion and marks stale calls interrupted. Its
restricted role has only the cleanup function. A five-minute cron starts making
requests only after a Vault-backed secret is configured by bootstrap.

The worker captures production `phone-` rooms with SIP participants, excluding lab
and verification probes. Each call loads a configuration with a three-second
budget, falling back to a cached published snapshot or the deployed initial snapshot.
It records the actual source/revision. Active calls never change configuration.
Archive retries are bounded by shutdown time; fatal crashes can lose unuploaded
audio. Missing/failed recordings are shown explicitly. SDK transcripts can be late
or incomplete. Six-digit codes are omitted from CRM transcript text. CRM retention
does not govern copies independently retained in LiveKit Agent Insights.

## Release sequence

1. Reconcile shared migration history. Apply **only**
   `20261006060755_voice_crm_workspace`, after CRM availability migration
   `20261006053509` and its voice/lookup prerequisites. Preserve the existing E2
   account, service-release, booking and unified-lead migrations. Never replay history.
2. Provision the two restricted logins and maintenance Vault secret with
   `scripts/bootstrap-voice-crm.js` using a privileged deployment connection.
   Recovery values are written first to ignored `data/voice-crm-credentials.env`.
   Existing logins cause a refusal, not an implicit rotation.
3. Deploy `voice-runtime`, `voice-maintenance` and the updated `crm-api` with server
   secrets. Runtime defaults disabled. Storage signing uses the existing server-only
   Supabase service credential, not the agent credential.
4. Export the voice project's latest verified production prompt history using
   `export_crm_configuration.py --output .local/crm-import.json`. Compare its source
   revision with the running agent before initializing CRM. Do not import lab defaults
   or an uncertain publication. Keep the existing business/persona mismatch handling.
5. Deploy the updated worker with `VOICE_CRM_ENABLED=true` and
   `VOICE_RUNTIME_SECRET`, then enable the matching Edge flag. Merge secrets without
   replacing the existing lookup/booking credentials or fallback prompt mount. Also
   configure the local publisher's environment so production publishing directs to
   CRM. Local lab tests remain available. Keep `VOICE_BOOKING_ENABLED=false` until
   real availability and its booking pilot are ready.
6. Publish the CRM frontend. Verify authenticated staff reads, unsigned/customer
   denials, private media access, observed revisions and a controlled phone call.
   No production sample leads or bookings should be manufactured by deployment.

Rollback: disable the CRM runtime flag on the worker to restore its retained mounted
configuration; preserve database records and maintenance cleanup. Configuration-only
rollback is a normal CRM publication. Report failed uploads, stale observations,
capacity conflicts and duplicate suppression using IDs/statuses, not caller payloads.
